# LinkedIn company publishing and post metrics

The transport supports organic company text posts and, behind a separate disabled-by-default gate, one approved PNG export. It does not upload video, publish personal-profile posts, enable Instagram publishing, or establish live platform acceptance. Facebook has its own text-only adapter.

## Approved image transfer

`LINKEDIN_IMAGE_PUBLISHING_ENABLED=true` on web and worker additionally enables single-image selection. This is not enabled by adding an API key. The user selects a retained export of the exact approved copy/composition in Publishing & analytics. Scheduling freezes its local ID, SHA-256, byte count, dimensions and approved headline as alt text; no client URL, object key, replacement copy or invented description is accepted. Scheduling must precede the export's expiry. The private bucket remains private.

The worker verifies the source manifest, renderer, copy/brand/asset permissions and blocking comments before reading the object, again after reading and before each transfer boundary. Stored bytes must match the fingerprint. A separate durable fence precedes `POST /rest/images?action=initializeUpload`. The returned image URN is recorded before the sole binary `PUT`. Only HTTPS `www.linkedin.com/dms-uploads/{matching-image-key}/uploaded-image/0` is accepted, with no redirects, credentials in URL, alternate ports or fragments. Upload URLs and raw responses are never stored or sent to the browser. Other upstream URL shapes deliberately fail closed until reviewed and tested.

An acknowledged upload is followed by a fixed-endpoint image read requiring exact URN, owner and AVAILABLE status. Pending processing returns a bounded safe retry **before any post submission**; the same saved URN is reused without another registration/upload. Three worker attempts bound this path. Unknown registration/upload outcomes remain held without repeating a write. An orphaned provider upload is possible after interruption; remote media deletion is not implemented. The guarded pre-post recovery below can close only a local attempt for which publication never began. Operator inspection must not clear fences or pretend a post exists.

The existing publication fence then permits one post attempt containing that image URN and approved alt text. Read-back verifies exact caption, image and description; lost post confirmation uses candidate-ID reads only. Metric reads require the saved image identity/description both before and after reading statistics. A changed image is excluded just like changed copy. This proves ID/description binding, not perceptual equality of LinkedIn's resized rendition or upstream image history. No visual fidelity score is fabricated. The metric count definitions remain v2; the text-only description below refers to the older transport lane.

Removing an export cancels its queued posts. In-flight/uncertain posts block removal and defer physical expiry cleanup until investigated; ordinary download expiry still applies. A published network copy survives local deletion and must be managed on LinkedIn. Processing retries or rescheduling cannot replace a saved image with another fingerprint. No generation credits or AI calls are involved in transferring an existing PNG.

Migration `20261019000000_social_image_transfer` adds media-transfer version, external image ID and acknowledged-upload fields, a binding constraint and per-account image-ID uniqueness. Synthetic restore tests preserve these alongside uncertain post receipts. UI checks cover exact-version selection, disabled capability, keyboard submission, focus on rejection, retained selection, mobile width and automated accessibility. Real rendered PNGs flow through the adapter/worker/database in local tests; provider responses remain fixtures.

Official contracts checked 18 October 2026: [Images API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/images-api?view=li-lms-2026-07), its linked [binary upload instructions](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/vector-asset-api?view=li-lms-2026-07#upload-the-image), and [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-07). Live acceptance must verify the actual upload URL shape, permissions, asynchronous processing and read-back fields for the configured API version before activation. Text-only behavior below remains unchanged.

## Configuration

### Closing an interrupted image attempt before posting

The operator-only `scripts/stop-unsubmitted-image.ts` defaults to preview. Supply exact `--organization`, `--business`, `--publication` and `--operator` values. Preview returns a state fingerprint and safe status, never credentials, source payloads or remote identifiers. Applying requires `--apply`, the unchanged `--expected-state-hash` from preview, and `--evidence` describing the operator's investigation. Evidence must not contain credentials or private customer content. Database access is privileged; there is deliberately no customer route for this operation.

Under the same business lock as publishing/reconciliation, it requires a valid immutable LinkedIn image snapshot, `NEEDS_RECONCILIATION`, no active lease, and **no** post-submission fence, candidate, verified ID, publication time or permalink. A null fence alone is insufficient for legacy text workflows. Changed state, concurrent/repeated requests, other workspaces and actual unknown post outcomes are refused. It does not require a live token or make network/provider calls. Successful application records `FAILED/PREPOST_IMAGE_STOPPED`, stops lookups, preserves all media and submission evidence, and writes an operator audit event. This terminal status cannot be rescheduled by the normal scheduling action. Local export removal may then proceed; any separate future attempt requires a newly approved creative version. A delayed worker cannot record a result or start a post after this transition.

This is **not** evidence that the image upload failed or that no private remote image remains. It neither deletes remote media nor resolves a post whose submission may have started. Keep that distinction in any retention/deletion response. No recovery operation was run on production records during implementation.

Keep both `LINKEDIN_PUBLISHING_ENABLED=false` and `SOCIAL_EXECUTION_ENABLED=false` until designated-account acceptance. Configure the existing LinkedIn credentials, supported version and verification expiry on **web and worker**. `LINKEDIN_CONNECTIONS_ENABLED` is also required to register the publisher. `SOCIAL_DATA_ENABLED` independently controls explicit account/profile reads; it is not a substitute for the per-post worker. See [activation checklist](ACTIVATION-CHECKLIST.md).

The adapter rejects unsupported account/provider/channel/format/media before HTTP. It rechecks application-bound token introspection, expiry, required scopes and approved company administration before submission, reconciliation and metrics. Role discovery is bounded to two pages of ten; it does not follow response URLs. All reads use fixed HTTPS endpoints, reject redirects, bound received bytes and time out. Errors never disclose raw responses or secrets.

## Submission and read-back

The existing schedule freezes the exact approved caption and brand version. Immediately before the remote write, `submission-journal.ts` locks the business and verifies the persisted payload, account, current encrypted credential and active submission lease, then records `submissionAdapterVersion`. This durable local fence permits only one POST attempt. It is **not** a claim that LinkedIn supports idempotency keys.

The adapter uses `POST /rest/posts` with organic public/main-feed text parameters. Only HTTP 201 with a valid `x-restli-id` is a candidate. It persists `candidatePostId` before `GET /rest/posts/{id}?viewContext=READER` and verifies exact ID, author, published status, timestamp, caption and absence of media/reshare/ad context. Only a verified receipt sets `externalPostId` and `PUBLISHED`. No permalink is invented.

Before any write, temporary rate/server failures may safely retry through the existing bounded worker policy. After the durable fence, **any** unknown response or failure remains uncertain; it does not resend. Known candidate IDs may be read back with the existing five-attempt reconciliation policy. A lost submission response with no candidate ID stays held for operator investigation. Empty search results or caption matching are not proof that no post exists. No customer endpoint accepts a fabricated receipt.

Migration `20261018040000_social_submission_journal` is additive. It adds the version/candidate fields, bounded-value checks and uniqueness of `(connectionId, candidatePostId)`. Do not drop those fields to retry a post. Interrupted publication state and candidate IDs are included in the synthetic restoration rehearsal.

## Metrics and learning boundary

For a verified app publication, the worker rechecks token/admin ownership and the exact published post, then requests organic share/UGC-post statistics for that company and ID. Company-wide aggregates are rejected as per-post observations. Lifetime snapshots are never added together. Missing values remain null. Engagements means likes + comments + shares, excluding clicks; the API version and definition are stored with each snapshot. Negative organic-like adjustments are accepted as a platform possibility, but prevent deriving a misleading nonnegative engagement total. Valid other metrics remain available.

Credential, account, post or payload changes during a request prevent snapshot persistence. Expiry/disconnection stops ingestion. Existing periodic collection, five-failure bounds and human-reviewed observational learning policies still apply. This release supplies per-publication evidence; text-only production does **not** by itself produce the two-format experiment cohorts required by the current learning evaluator. It is not evidence of causal or creative improvement.

The v2 metric definition additionally requires the frozen approved caption, exact verified publication time, public/main-feed text-only content and absence of reshare/ad context before and after statistics retrieval. Detected drift sets `metricsInvalidatedAt`, stops polling and excludes all readings for that source from summaries and future learning; published receipts and historic snapshots remain. Previously promoted experimental memories are revalidated before use. Older LinkedIn v1 observations are retained but excluded, not silently upgraded. Malformed replies and permission/network failures remain transient failures rather than definitive edit evidence. Edits made and reverted between observations cannot be guaranteed detectable.

## Recovering stopped metric checks

After the account access problem is resolved, a workspace owner/admin can use **Publishing & analytics → Resume metric checks** on a stopped publication. This queues a read-only worker check. It does not publish, approve, generate or spend creative credits. The request checks the current session/auth version, workspace MFA, role, exact business, encrypted credentials, frozen publication and registered metrics-capable adapter. It refuses invalidated sources, posts outside 30 days, active leases and existing scheduled/backoff work. A version expectation prevents duplicate/stale browser requests; the business lock enforces one-hour per-post cooldown and six successful recovery requests per UTC day. The HTTP endpoint separately allows at most 12 attempts per user/hour. Recovery resets only metric failures and polling state and writes a safe audit event. It cannot create a missing provider mapping, widen grants, re-approve externally edited content or clear a publishing reconciliation hold. Unsupported provider controls explain why recovery is unavailable. Credentials and execution flags remain operator-managed.

The share-statistics documentation names `rw_organization_admin`, whereas the organization-role documentation also describes reporting under `r_organization_admin`. The application currently requests the latter plus organization social read/write. Verify the actual app's approved reporting access; denied reporting remains unavailable and must not be relabelled as successful analytics. A necessary scope expansion requires a reviewed code/configuration update and reconnection.

## Verification

Tests exercise the real transport with injected HTTP: valid submission/read-back, preflight denial, revoked/expired/foreign app grants, wrong accounts/captions, malformed replies, unknown writes, safe retry boundaries, known-ID-only reconciliation, negative/missing statistics and company/post metric binding. Database tests exercise scheduling through the real adapter and durable journal to a verified receipt and metric snapshot, concurrent fencing, changed-context denial and no duplicate POST. These are not real platform publications.

Before activation, complete the designated company's OAuth, explicit text-post consent, one successful scheduled publication/read-back, actual organic metrics, denial/expiry/role-loss tests and worker configuration verification. No real post or paid AI call is authorized merely by this document.

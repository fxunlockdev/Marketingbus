# Static exports, social orchestration and measured experiments

## Static composition

Design studio builds an editable JSON layer document from a current copy revision and approved assets only. Placement uses the original normalized raster bytes, checked against their stored SHA-256. It does not ask an image model to redraw logos or products. Layout versions are immutable; editing supersedes the preceding version. Copy approval and visual approval are separate. Brand/version changes or asset revocation block future export. Stale edits fail rather than overwrite another editor's work.

Saved draft previews are permitted before approval. Final PNG/SVG/JSON exports require approved current copy, approved current composition, current confirmed brand and still-approved assets. Every render rechecks permissions after asynchronous storage work. PNG is rasterized by Sharp; SVG escapes text and embeds trusted raster bytes only, with no remote URLs or scripts. Text uses measured bundled Figtree outlines, kerning and ink bounds; overflow and unsupported characters refuse export. Sizes: 1080×1080, 1080×1350, 1080×1920 and 1200×628. These are canvas presets, not a guarantee of every platform's current media rules. Downloads cannot be recalled after revocation.

Authenticated downloads and private immutable saved PNG exports are implemented. The Gemini supporting-artwork workflow is described in [image production](IMAGE-PRODUCTION.md). Approved single-image delivery is implemented for LinkedIn, Facebook and Instagram behind separate provider gates; social video delivery remains unimplemented. No provider call or AI credit is consumed by deterministic composition.

## Social safety boundary

`configuredSocialAdapters()` registers implemented publishers only with explicit provider enablement, complete private credentials and current operator verification deadlines; it remains empty by default. The OAuth registry separately covers Facebook Pages, Page-linked Instagram professional and LinkedIn company accounts. A separate `SOCIAL_DATA_ENABLED` gate controls bounded account-data reads. Setting `SOCIAL_EXECUTION_ENABLED=true` does not activate publishing or authorization by itself. No fixture adapter is registered. Account records are created only from verified server-side grants followed by explicit account selection; there is no public arbitrary-token ingestion endpoint. See [account-data configuration and acceptance limits](SOCIAL-ACCOUNT-DATA.md).

### Account authorization and selection

The application implements an authorization-code flow with S256 PKCE by default, random one-use state stored only as a hash, distinct provider callback paths and a fixed server-owned redirect URI. LinkedIn and Meta use separate confidential web modes restricted to their providers and exact authorization endpoints, not a generic PKCE downgrade. Native PKCE support is not assumed to apply to web clients. Every adapter must verify its official endpoint, authentication method, token audience, account-management rights and required permissions before registration. No arbitrary endpoint or token may be submitted by a customer.

An owner or admin starts a ten-minute request from a specific business and authenticated browser session. The callback checks that session, destination, current role, expiry and configuration, consumes the request before exchanging its code, and never retries an uncertain exchange. State, authorization codes and verifiers are not forwarded to the return page. Application errors contain no provider response details; platform/proxy access logs still require a separate query-redaction review before live OAuth acceptance.

Account choices and tokens stay encrypted with business, session and flow context. Only opaque choice IDs and labels reach the browser. The callback does not create a connection: an authorized owner or admin must choose one account. Selection, encrypted permanent credentials, temporary-secret removal and the audit event commit together. Session revocation, role changes, expiry, changed adapter configuration, missing permissions and a competing selection block activation. Cancelling during exchange discards its late result. A new request replaces this session's older request for that business/provider. Logout deletes its temporary flows; bounded worker cleanup removes expired rows independently of paid execution. Backups and external platform grants have separate retention/revocation requirements.

The Connections screen contains publishing destinations only, shows actual scoped account records and allows request cancellation/refresh. It explains unconfigured Instagram/Facebook/LinkedIn setup and labels X/YouTube as planned. The return page offers scoped account selection or a generic recovery path without reflecting external query data. Meta and LinkedIn discovery, bounded account-data views and approved single-image publishing are implemented; automatic token refresh/provider revocation, social video and live acceptance remain unfinished. Refresh limits, null metrics, retention and account-specific data semantics are documented in [account data](SOCIAL-ACCOUNT-DATA.md).

Scheduling binds an exact approved current revision, frozen payload/hash, account and timezone. Rescheduling cannot change that payload hash. Text-only posts support Facebook/LinkedIn; Instagram requires an approved square/portrait export and bounded JPEG delivery. All three single-image lanes use durable media/post fences and provider-specific authorization/read-back. See [LinkedIn](LINKEDIN-PUBLISHING.md), [Facebook](FACEBOOK-PUBLISHING.md) and [Instagram](INSTAGRAM-PUBLISHING.md) for current supported profiles and live-acceptance gates. At execution, the worker rechecks brand, approval, snapshot, account status/expiry and placement before marking SUBMITTING. Invalid persisted payloads and unreadable credentials stop that item without repeatedly blocking the queue. Safe retries require the adapter to establish that no publication occurred, with a maximum of three submission attempts. Timeouts, process death and malformed receipts become NEEDS_RECONCILIATION, never blind retries.

The worker now checks one due uncertain publication per social tick using lookup only. Each lookup has a two-minute lease and a 45-second adapter timeout. It makes at most five checks with one-, two-, four- and eight-minute delays between inconclusive results. Counts and eligibility times persist across restarts. Empty results do not prove non-publication; timeouts and malformed receipts remain unconfirmed. Invalid snapshots, expired accounts and unavailable decryption stop lookup for operator attention. A crashed fifth check is also marked stopped. No branch resends the post.

Before saving a receipt, the worker checks the original payload hash, destination account, encrypted credential, account status/expiry and current lease again. Stale responses cannot finish another worker's attempt. Receipt persistence and its audit event share one transaction. Publication history shows the lookup count, next eligible check or operator-review requirement without exposing tokens or payloads. Official adapters must still prove account/content read-back; this contract alone is not platform acceptance.

### Operator lookup recovery

After investigating a stopped outcome, a privileged server operator can use `scripts/resume-social-lookup.ts` with `--publication`, `--operator`, `--evidence` and explicit `--resume-lookups`. Evidence must describe the account/snapshot or credential repair and must not contain secrets. The command refuses active leases, confirmed outcomes, invalid snapshots and unusable credentials. It records the previous check count and operator evidence before reopening at most five lookup checks; concurrent/replayed requests do not reset an already-open window. It never assigns an external post ID, changes the uncertain status, submits content or settles credits. There is no customer HTTP endpoint for this operation. A dedicated operator console, alerts and provider-specific investigation tools remain pending.

New copy versions, rejection, unscheduling and brand changes invalidate queued publication. Content edits remain blocked during uncertain or in-flight submission so they cannot imply cancellation of a remote write already made. Local account disconnection is now separately allowed with explicit confirmation, current owner/admin/session/MFA checks and the exact saved authorization version. It erases the local token, permissions and saved account snapshot, cancels queued posts and same-provider pending OAuth flows across sessions, and stops metric checks. Published receipts and metric history remain. Submitting posts become uncertain; existing uncertain posts retain their candidate IDs and submission fence. An active request may still finish remotely and cannot be recalled. Late results cannot overwrite the disconnection or reschedule its checks. No remote post, grant or other business connection is deleted.

Disconnection is managed in customer Connections, not the publishing dashboard. The legacy sessionless disconnect action is rejected. Each verified reconnect increments `authorizationVersion`; stale browser requests cannot disconnect a newer grant. A reconnect to the same verified account is permitted once any retained in-flight lease has ended, even if a post remains uncertain. It does not reopen cancelled publications, metric polling or disconnection-stopped reconciliation. A privileged operator must investigate and explicitly resume lookup with evidence; there is never an automatic resend. An already-disconnected account is a no-op only with its current version. Platform-level revocation, automated refresh, remote deauthorization callbacks and complete retention/export policy remain separate work. The screen tells the customer to revoke the app in the network settings for remote authorization removal; it does not claim that local deletion does this.

## Metrics and learning

Snapshots preserve unsupported metrics as null, not zero, and are deduplicated by publication/observation/definition. Dashboard totals use only the latest lifetime reading for each of at most 500 recent published posts, separately grouped by account and metric definition. They are not date-range increments. Coverage/staleness is visible; summed reach is not unique people and engagement is not conversions. Metric sync is leased, bounded, age-aware and stops after repeated failures or thirty days. LinkedIn organic post mapping and exact-source drift checks are implemented but not live-accepted; Facebook/Instagram post mappings remain unimplemented and create no fake snapshots.

An experiment proposal requires two formats on one account/definition, at least five mature posts per format and 1,000 impressions each. A relative/absolute observed engagement-rate difference only produces a hypothesis. Nonrandomized audience/topic/timing differences may explain it; it is not statistically validated causal learning. Promotion requires explicit human confirmation for the current brand, creates one scoped experiment memory and invalidates offered generation quotes. Reverting removes exactly that memory. It does not train model weights, rewrite skills or initiate publication/spending. Weekly planning and bounded copy authorization exist; mixed-media autopilot and measured improvement remain incomplete.

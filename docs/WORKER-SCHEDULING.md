# Production worker scheduling

## Weekly planning context isolation

Runtime `studio-v65-weekly-context-isolation` pauses an individual recurring policy when its retained brand fails validation or its planning knowledge exceeds the existing context limits. Previously this transaction rolled back and left the same oldest policy due, repeatedly delaying other businesses. Preparation now completes bounded knowledge reads sequentially, records one fixed, content-free `WEEKLY_POLICY_PAUSED` audit event under the business lock, and disables that policy. The next tick can select another due business.

No plan, generation job, quote or credit reservation is created for the invalid context. Previously authorized jobs, customer holds and supplier authorizations remain unchanged; existing media lanes still check current authorization before accepting new work. Repairing the context alone does not resume the policy: an owner/admin must explicitly save recurring authorization. Concurrent planner ticks cannot duplicate the pause. Unexpected or infrastructure errors still propagate and roll back, including the schedule update; they are not mislabeled as bad customer context.

Database tests cover invalid brand fields and excessive preference count, individual length and total length; cross-tenant progress; overlapping ticks; administrator-only resume; infrastructure rollback/recovery; and preservation of an earlier authorized cycle. A browser journey checks the disabled recurring control, redacted response, keyboard reauthorization and unchanged credits. This is a targeted planning fairness fix, not a complete load/capacity guarantee or customer-facing failure notification system. See BUILD-STATUS.md for actual verification and deployment state.

## Copy claim ownership and late-result fencing

Runtime `studio-v63-copy-lease-fence` binds submission and delivery to the exact claimed job, organization/business, kind/key, quote, reservation, attempt count, lease and payload. A short row lock protects each boundary. The lease must still be live before submission and delivery; status alone is not ownership. A worker returning after replacement or recovery cannot clear the new claim, settle its hold, deliver a creative or overwrite the retained recovery reason. No row lock spans the provider request.

If the same unreplaced claim expires before submission, failure releases unused customer credits. Expiry after submission leaves uncertainty and holds for operator reconciliation, even if a late response has arrived. A claim whose identity changed is left untouched for its current worker/recovery process; this guard does not automatically repair corrupt records, retry a provider or extend leases. Scoped cleanup also preserves newer creative states. Database tests inject replacement leases, attempt/payload changes, elapsed time and recovery while a fixture provider response is pending. These are deterministic lifecycle tests, not a live supplier or distributed-host failure drill.

## Hard-stop recovery checkpoint

Runtime `studio-v61-crash-recovery` closes a copy-recovery visibility gap: after an expired `SUBMITTING` lease, the job and its scoped quote enter reconciliation and the still-queued creative now enters `NEEDS_RECONCILIATION` in the same transaction. Only the recovery winner updates the associated state. Exact organization/business/item scope is checked; newer creative states are preserved. Credits remain held and supplier submission is never automatically repeated.

The process regression starts the actual worker against a newly created, migrated, synthetic local database with all external execution disabled and no inherited provider/storage credentials. It terminates that worker with `SIGKILL`, verifies retained jobs/heartbeat, expires only fixture leases, and overlaps two real replacement workers. Pre-submission work becomes queued; uncertain submission remains fenced. Another polling cycle leaves attempts, reservations, credit journals and both tenant wallets unchanged, with no generated revision. Both replacements then exit cleanly on `SIGTERM` and remove their own heartbeats. Separate database cases preserve newer creative state and reject cross-business quote references.

This is a real process hard stop and concurrent restart, but the submission fences are synthetic: no supplier call is in flight, and lease expiry is advanced in the disposable database rather than waiting five minutes. It does not prove container/host failure recovery, remote-provider reconciliation, realistic load, alert delivery or capacity. See BUILD-STATUS.md for test and deployment evidence.

## Current: bounded independent groups

Runtime `studio-v48-social-access-lifecycle` adds a 25th lane, `social-access-expiry`, to maintenance. It removes one expired grant per tick without provider calls or execution flags, using the same business lock as connection/publication work. This does not introduce another process, replica or paid operation. See [access lifecycle and recovery](SOCIAL-ACCESS-LIFECYCLE.md).

Runtime `studio-v47-weekly-mixed-media` adds the 24th lane, `weekly-video`, to the same sequential production group. It advances one approval-gated storyboard/shot/assembly/render transition, sharing the existing weekly credit ceiling and durable provider workers. It adds no process, replica or parallel paid generation. See [mixed-media behavior](WEEKLY-MIXED-MEDIA.md).

Runtime `studio-v46-isolated-worker-groups` partitions the existing 23 workflows into six fixed asynchronous groups inside the existing worker. Production retains every AI generation/authorization, clip normalization, motion rendering and corresponding recovery lane in one sequential group. Publishing/reconciliation, metrics, delivery/payments/planning, website intake and maintenance have independent loops. A slow asynchronous media request no longer prevents publishing or metrics from getting their next turn. Each group still performs one bounded attempt per lane, followed by the existing five-second pause. No paid-generation parallelism, extra replica, execution flag, daily authorization ceiling or spending limit is introduced.

Readiness writes are shared and coalesced to at most one attempt per five seconds. Their persisted timestamp is the **oldest group checkpoint**, captured before asynchronous readiness work, not the time a busy peer last finished. A stalled group or a stalled database write expires local health and matching durable admission after the existing 120-second deadline. Database failure pauses subsequent group cycles without leaking raw errors, and retries readiness only after the polling interval. A paused-but-responsive worker remains healthy with paid execution disabled. Successful lane failure handling is not proof that the underlying integration works.

Shutdown wakes all idle loops, prevents later lanes from starting, waits for active operations and serializes heartbeat removal after any in-flight readiness write. Retention tasks are now awaited rather than left running after the worker closes its database. Existing leases, source rechecks, approval checks, immutable submission fences and recovery limits remain unchanged. There is no timer-based retry of uncertain writes and no concurrent mutation within a group.

This is asynchronous scheduling isolation, **not operating-system process isolation**. Synchronous event-loop blocking, container failure, provider rate limits, database contention and the single global CPU slot still apply. Publishing throughput retains its existing bounded cadence. Separate process roles, measured queue/service objectives, load/chaos tests, alerts and an operator-approved capacity plan remain required for 500–700-business readiness.

Verification adds deterministic blocked-generation tests showing independent publishing/metrics progress, single-generation concurrency, duplicate-lane rejection, coalesced writes, stalled-group/database health expiry, failure recovery and shutdown draining. The real child-process/database test verifies startup, current runtime, clean SIGTERM exit and heartbeat removal; a database test preserves an old group checkpoint and rejects future timestamps. These tests do not call a paid provider or establish a production-load SLA.

## Earlier sequential scheduling and weekly-image behavior

Runtime `studio-v36-weekly-images` adds a separate, paid-execution-gated `weekly-image` authorization lane. Existing policies default to images disabled. An owner/admin can opt into one initial image for each weekly static item after its copy job completes and its current copy is human-approved. Copy and image authorization share the same cumulative weekly credit ceiling; authorization runs in the same transaction as supplier/wallet/storage admission. Generated artwork still requires visual review and final composition approval. This lane never publishes, generates video, automatically revises imagery or replaces manually started image work.

The media phase has an independent two-minute lease and five-minute retry-of-readiness delay. Waiting for review or an active image job is not a model retry and does not monopolize other businesses. An already attached, unexpired offer can resume after a worker restart without another quote. Authorization/configuration/approval failures stop the media phase and cancel unaccepted offers; they do not automatically retry or reset spend. A changed brand, policy, authorizer or UTC week stops further media authorization. Stopping a run works even when copy authorization has finished and preserves already-authorized jobs, holds and cumulative credits. The operator queue report includes blocked, overdue and expired-lease media phases without treating an active review delay as a failure.

Runtime `studio-v27-fair-worker` replaces early-loop continuation with one sequential attempt per enabled workflow per cycle. Continuous copy work no longer skips social publishing, reconciliation, metrics or website intake. Continuous clip normalization no longer skips approved motion rendering. Existing global/daily budgets, CPU leases, current-role/approval checks and single-submission policies still govern each worker.

Every workflow has its own failure boundary. A failed brand, image, payment, recovery or social operation records only its code-owned lane label and does not prevent independent lanes from running. This is not a generic provider retry mechanism: uncertain external writes stay governed by the existing durable job/reconciliation contracts. Raw errors, tokens, URLs and content are not logged by the scheduler.

Readiness is established at the beginning of each cycle and refreshed between lanes when at least 30 seconds have elapsed. A readiness/database failure stops the cycle and makes health unavailable. There is no background heartbeat timer masking a stuck operation. A single genuinely stuck lane can still exceed the 120-second health deadline; independent process/container supervision remains an operational requirement, not something this scheduler certifies.

Shutdown is checked before and after readiness and before each lane. An already-running bounded operation may finish; no later lane starts. The process removes its heartbeat and closes the database/health server. There is no extra five-second sleep after shutdown. Existing hard-stop behavior remains.

The scheduler does not introduce parallel paid jobs or new infrastructure. Fast/empty cycles still have a five-second delay. A cycle containing slow provider/media work may take longer; this is not a precise execution-time SLA. Retention remains bounded background work with existing object leases/tombstones; full per-lane process isolation, metrics/alerts and load/chaos acceptance remain unfinished.

Verification includes deterministic tests for busy/failing lanes, disabled paid work, changing readiness, no overlapping mutations, cancellation and clean error projection. A local-only child-process test launches the actual production entrypoint with no inherited supplier/storage credentials and every execution flag disabled, verifies HTTP health and the persisted runtime heartbeat, then sends SIGTERM and verifies a clean exit and heartbeat removal. It does not execute live provider work or prove production load capacity.

## Capacity gate for 500–700 businesses

Read-only source audit, 19 October: v45 had 23 sequential lanes and a five-second delay after each cycle. The v46 groups above remove cross-group asynchronous waiting, but retain the five-second per-group delay. Motion rendering and clip normalization still share one global active-processing slot (`pg_advisory_xact_lock(71403219)` plus RUNNING/STORING counts). `motionDailyLimit()` rejects values above 100; final renders and uploaded video/audio processing consume the shared global daily authorization pool. Adding worker replicas alone does not remove either constraint.

These are safe pilot bounds, not a capacity claim. For illustration, 700 businesses requesting one final render each on the same day exceed the current 100-authorization ceiling even before source normalization. A useful load test must include realistic generation/normalization latency and simultaneous scheduled posts, not merely 700 empty workspace rows or unauthenticated health requests.

Before claiming the target capacity: isolate latency-sensitive publication/reconciliation from long-running media work; add explicit bounded worker/concurrency roles with matching readiness; retain distributed admission, immutable write fences and global spend enforcement; define tenant fairness and operator-adjustable capacity within measured resource budgets. Then run paid-provider-free isolated database/HTTP/encoder load and crash tests, recording queue age, scheduling lag, p95 request latency, database connections/locks, CPU/memory and per-workspace denial. Verify backup/restore and alert routing separately. Do not raise production limits or provision replicas merely because the feature regression suite passes.

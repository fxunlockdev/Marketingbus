# Instagram approved-image publishing

Implemented lanes: one approved square (1080 × 1080) or portrait (1080 × 1350) image with its exact approved caption and headline-derived alt text; and a separately gated approved final portrait Reel (details below). Captions have a conservative application ceiling of 2,200 JavaScript string units. This is not Stories, carousels or live Meta acceptance. Other profiles remain explicitly unsupported, rather than silently cropped or posted without media.

## Approved Reels

Runtime `studio-v42-instagram-reels`, migration 49, adds `INSTAGRAM_REELS_ENABLED=false` by default, in addition to every existing Instagram publishing gate. The customer chooses a reviewed final render belonging to the exact approved copy version. The same normally planned Instagram creative can have both image and video work in Asset studio; Publishing media explicitly selects which reviewed output to publish. The immutable publication format follows the selected export, not just the initial plan label. One copy version can still be published only once per account; changing a saved media choice requires a new approved copy version. The checkbox to also share to feed defaults to false and is frozen with the scheduled payload. No customer URL, bucket key, arbitrary upload or unreviewed generated shot is accepted.

Supported application output is 720×1280 portrait H.264 MP4, 24 fps, 3–30 seconds and at most 20 MiB; approved optional instrumental audio is encoded by the existing renderer as AAC 48 kHz/128 kbps. These are application bounds, not the full Meta profile. The exact render hash, length, dimensions, duration, storyboard hash, current shot reviews, brand/copy and underlying media rights are checked before scheduling, transfer and the post fence. Expired, superseded, changed or revoked work fails closed. Downloadable originals remain private.

The container request uses `media_type=REELS`, `video_url`, the exact caption and explicit `share_to_feed`. Its adapter journal version is separate from the existing image lane, preserving in-flight image compatibility. A known acknowledged container in `IN_PROGRESS` may be polled once per minute, for at most 15 total attempts and without extending its 15-minute media capability. It cannot repeat container creation. Exhaustion or expiring delivery holds the attempt for operator investigation; a known finished container alone may cross the separate publication fence. Lost acknowledgement never causes an automatic duplicate write. Exact owner, ID, caption, VIDEO/REELS and timestamp are required on post readback. The existing pre-post recovery command supports inactive Reels with no post fence/candidate/receipt; it does not delete remote containers or retry publication.

Delivery uses the existing hash-only capability and current authorization checks. MP4 bytes are delivered unchanged after integrity checks, with one bounded byte Range per GET; multipart/invalid ranges are rejected. Explicit HEAD returns metadata without reading storage. HEAD and GET share the 12-read allowance and eight-operation per-process cap; there is no capability renewal. Revocation is checked again after storage I/O. Infrastructure path-log redaction, real Meta Range/fetch patterns and suitability of these bounds are mandatory live acceptance checks, not assumed from fixtures.

Reel metric collection is independently gated by `INSTAGRAM_REELS_METRICS_ENABLED=false`. The image metric flag cannot activate it. See the Reel analytics contract below; fixture coverage does not establish live video analytics or measured learning.

Provider contract evidence is Meta's [Reels publishing collection](https://www.postman.com/meta/instagram/folder/y6xustx/reels-publishing), [Instagram API collection](https://www.postman.com/meta/workspace/instagram/documentation/23987686-9386f468-7714-490f-9bfc-9442db5c8f00), and the official SDKs linked below. Live acceptance must verify required readback fields, actual processing transitions, feed choice, fetch limits and real post IDs on the designated account. Keep the gate disabled until that succeeds. No real Meta posts or paid model calls were used during implementation.

## Activation and current evidence

Keep `INSTAGRAM_PUBLISHING_ENABLED=false` until designated-account acceptance. Registration also requires `SOCIAL_EXECUTION_ENABLED=true`, `INSTAGRAM_CONNECTIONS_ENABLED=true`, valid Meta application credentials, a verified API version/deadline and a public HTTPS `APP_ORIGIN`. Configure web and worker consistently, including the same build, private storage and encryption keys. This uses the existing Facebook Login route: a Page access token for a Page-linked Instagram professional account. The current grant must match the application, required scopes, Page identity and linked Instagram account. Granular permission targets are checked before writes or receipt reads. Customers connect through OAuth, never by providing their password or our app secret.

The provider contract is based on Meta's official [IGUser SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/iguser.py), which defines image-container parameters and the `media_publish` creation-ID edge, and [IGMedia SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/igmedia.py), which defines owner, caption, alt text, media/product type, timestamp and permalink fields. Current developer-page access was unavailable during implementation. SDK/schema support is not proof that a particular application/API version has access to each field. Live acceptance must verify the actual account, permissions, status transitions and mandatory read-back fields before activation.

## Approval-to-delivery contract

Scheduling selects a retained private export for the exact approved copy version. The immutable payload binds its PNG hash, byte length, dimensions and headline. Current brand, copy, layout, source rights, blocking comments, export retention and ownership are checked before transfer and again before the post fence. Unsupported text-only, landscape and story exports are refused. Original saved PNG downloads remain unchanged.

The worker verifies the private PNG's length and hash, then produces a delivery-only JPEG: no resize, white transparency flattening, sRGB, quality 95 and 4:4:4 sampling. Metadata is stripped. Source decode is bounded to 2 million pixels, a five-second sharp timeout and two conversions per process; JPEG output is capped at 4 MiB. These are application bounds, not an exhaustive statement of Meta limits. Both runtime codec versions and the exact JPEG fingerprint/length are bound to delivery. Different worker/web bytes or versions fail closed. This preserves composition geometry, not lossless image identity after JPEG conversion or Meta processing.

Meta must fetch `image_url`; the storage bucket is never made public. A 256-bit random bearer capability creates a single temporary application URL. Only its SHA-256 hash is stored. The raw token is sent once to Meta; it is not returned in customer APIs, persisted in audit events, or included in application error messages. Possession of the temporary link permits access to that exact image, so it is confidential even though it is not an OAuth credential.

The grant expires after 15 minutes, permits at most 12 reserved reads and cannot be renewed after the media fence. Reservations are serialized under the business lock; failed storage/conversion attempts still consume their allowance. At most eight delivery operations and two conversions run concurrently per web process. Source bytes, JPEG fingerprint and current approval are checked again after I/O. Disabled execution, terminal/uncertain status, expired lease, post submission, disconnection, reauthorization, source/approval/brand changes or export expiry revoke further delivery. Already-downloaded bytes cannot be recalled from Meta.

Images are delivered by GET; image HEAD is denied. Reels additionally support bounded Range GET and metadata HEAD as described above. Responses use no-store, no-referrer, nosniff, no-index and a restrictive CSP; unavailable capabilities return an empty 404. No cookies, public S3 URL, redirect, customer URL or provider token is used. No permanent generated-media CDN is created.

Before activation, verify edge/access-log handling of this route. Infrastructure may log request paths containing the short-lived capability; restrict log access, retention and forwarding and configure route redaction where available. Do not enable request-body capture for outgoing Graph calls. Application bounds are not a distributed WAF or load-test certification. Confirm real Meta fetch retries fit the expiry/read/concurrency limits, and review production edge controls rather than increasing limits without evidence.

## Durable submission and recovery

1. Verify grant, exact private source and JPEG; acquire the durable media fence.
2. Issue the one-use grant, recheck current authority, submit one `/{ig-user-id}/media` request containing image URL, exact caption and alt text, authenticated with the Page token and app-secret proof.
3. Persist the returned numeric container ID and acknowledgement. `mediaUploaded` means container acknowledgement for this adapter, not completed processing.
4. Read `id,status_code` for that exact container. `IN_PROGRESS` returns a bounded retry without new container or URL; the shared worker permits at most three attempts. `ERROR`/`EXPIRED` fail locally. Unexpected or already-`PUBLISHED` status without a known post is uncertain. Missing acknowledgement is never retried as a new write.
5. Only `FINISHED` may cross the separate durable post fence and make one `/{ig-user-id}/media_publish` call using the recorded creation ID. Persist its returned numeric media ID before read-back.
6. Accept only an exact ID, owner, approved caption, approved alt text, IMAGE/FEED type and valid timestamp. A permalink is retained only if it is a safe Instagram HTTPS URL. The worker additionally checks the receipt against the local creation time and current connection context. There is no caption-based search, fabricated receipt or inferred success.

Lost write responses, malformed receipts and changed authority remain uncertain. Reconciliation reads only the known candidate with the recorded container journal; it never uploads or publishes again. The expiry of a URL or absence of a candidate does not prove no remote object exists. No automatic remote-container deletion is implemented. A preview-first operator stop can close only an inactive approved-image attempt with no post fence/candidate/receipt and explicit investigation evidence. It preserves possible orphan metadata and never repeats a write. The same guarded recovery now covers Facebook images, correcting an earlier documented capability that was still restricted to LinkedIn in code.

## Metrics, testing and release limits

### Reel analytics

Runtime `studio-v43-reel-metrics` adds native Reel lifetime views, reach and total interactions using the existing nullable metric storage. It requires separate `INSTAGRAM_REELS_METRICS_ENABLED=true` acceptance on web and worker, in addition to the configured Instagram adapter. It does not require enabling feed-image metrics, and does not activate publishing. The app's verified Reel receipt, immutable video payload, numeric container identity, account, exact caption, VIDEO/REELS and publication timestamp bind the read. Reel source reads omit image-only alt text. Post identity is checked before and after the bounded insights read. Changed-source invalidation, reconnect-race rejection, five-failure backoff, polling cadence and deadline are shared with feed images.

Publication and known-receipt reconciliation schedule collection only if that media type has an enabled reader. Old published Reels do not start collecting merely because the flag changes: an owner/admin can explicitly resume an eligible post from the last 30 days, with session/MFA checks, no existing lease/backoff bypass, once-hourly per-post and six-per-business daily bounds. Unsupported stale tasks stop without making provider requests or claiming a source edit. Reads never upload, republish or spend generation credits.

Snapshots use `instagram-reel-views-reach-total-interactions-<API version>-v1`, separately grouped from feed-image readings. The dashboard rejects swapped feed/Reel definitions and damaged frozen payloads; missing data remains unavailable and zero stays zero. Native views are not impressions, completed plays or unique viewers. Reach is summed per-post reach, not a deduplicated audience. No paid/organic split, watch-time, completion-rate, conversion or causal claim is inferred. The current impression-based learning policy excludes these snapshots. Broader video metrics and a validated view-based experiment policy remain work, not enabled by this release.

On 19 October 2026 the official IGMedia and InstagramInsightsResult SDK sources below were rechecked for the media insights edge, native metric names and response containers. The developer reference returned 429 and the public Postman page did not expose its collection body. SDK declarations alone do not prove that this application's API version and Reel account return the requested fields. Keep the new gate off until designated-account acceptance verifies actual response identities, lifetime periods, scalar/null shapes, quotas, permission loss and external caption changes against Instagram. Local HTTP fixtures, real local rendering and database/browser tests are not real Meta acceptance. No paid calls or real posts are required for the code verification.

Post metrics are separately gated by `INSTAGRAM_METRICS_ENABLED=false` by default. Enable only after the live acceptance below, consistently on web and worker, with the existing social/Instagram connection/publishing gates and current Meta configuration. Account-data refresh remains separate. Previously published posts with stopped polling can use the existing owner/admin read-only recovery flow after activation; changing a flag does not automatically reopen old work.

Runtime `studio-v40-instagram-metrics` adds native lifetime `views`, `reach` and `total_interactions` for this implemented single-image FEED lane. Views have their own nullable database column; they are never renamed impressions or video views. The dashboard labels them explicitly, preserves unknown values separately from zero and shows per-metric post coverage. It does not assert organic/paid separation, distinct audience across posts, conversions or causal improvement. Current impression-based learning does not accept these view-based readings; a validated view-based evaluation policy and broader video publishing remain future engineering work.

The reader revalidates the app-bound Page token, granted insights permission, target scope and linked Instagram identity. It reads the exact post before and after the insights request and compares owner, caption, alt text, IMAGE/FEED type and publication time against the frozen receipt. A verified change invalidates attribution, stops polling and excludes historical readings from the dashboard; receipts and snapshots remain for audit. A malformed response or permission/network failure is not proof of an edit and follows the shared bounded backoff. Same-token reauthorization during a read now also rejects its late result. These are observed-state checks: edits reverted between observations and every possible distribution change are not detectable.

The transport is bounded to five authenticated reads per attempt: token inspection, Page/link identity, post, insights and post again. It uses the existing 30-second worker deadline, response-size limits, lease and failure cap. It never follows provider pagination, submits content, fetches media or spends creative credits. An insights row must belong to that exact media ID and named lifetime metric, be unique and contain one unambiguous scalar representation. Missing rows/empty values stay null; malformed, negative, oversized, duplicated, cross-media and breakdown responses are rejected. Provider error bodies and token-bearing URLs do not escape into customer messages.

Contract evidence: Meta's official [IGMedia SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/igmedia.py) declares the media insights edge and metric/period parameters; its [Insights result schema](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/instagraminsightsresult.py) declares the selected metrics and response containers. The [media insights reference](https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/insights/) and [insights guide](https://developers.facebook.com/docs/instagram-platform/insights/) returned HTTP 429 during this implementation. SDK declarations do not certify per-account metric availability or semantics. Keep the feature disabled until the actual version/account response and dashboard comparison pass acceptance; no secondary-source assumptions enable it.

Confirm request quotas and no paid/organic conflation. Record the accepted API version and verification expiry. A successful fixture or new key does not satisfy this gate.

They cover cross-workspace access, roles, changed permissions, caps, expiry, reauthorization, approval races, unknown writes, competing workers, SQL constraints and safe operator recovery. Credentials alone do not pass these tests. No actual Instagram call/post was made during implementation.

# Lower-footprint Firecrawl deployment components

This is a **locally verified extraction path, not an enabled production scraper**. Marketingbus retains its durable job queue, per-business cache, import consent and evidence review. The gateway uses the pinned Firecrawl standalone Markdown engine instead of a second six-process API/queue harness. Production images, hosting isolation and full workload acceptance are still required before changing the application extraction gate.

## Network boundaries

`public-egress-proxy.mjs` is the only component that needs internet access. It accepts authenticated CONNECT requests to public HTTPS port 443 only. It validates every resolved address, rejects mixed private/public answers, and connects directly to a validated numeric address without a second DNS lookup. It does not cache DNS answers. It caps concurrency, connection duration and aggregate bytes; it does not log URLs, credentials or response bodies.

`browser-service.mjs` must run on a network with **no direct internet access and no application/database peers**. It reaches only the private egress proxy; its caller is the isolated scraper worker. A proxy flag alone is not network isolation. The browser has no customer sessions, AI keys, application credentials or shared profile directory. The service opens Chromium only for an admitted job and closes it before returning the response. Health checks do not start Chromium. It denies downloads, WebSockets, mutation requests, non-HTTPS addresses and unused image/media/font requests. Cross-origin main-frame navigation is rejected; same-origin redirects retain the final URL. JSON requests are limited to 4 KB, page HTML to 2 MiB and each job to 30 seconds. There is one job at a time and no internal queue or automatic retry.

This deployment profile is for website text evidence, **not website asset downloads or arbitrary browser automation**. It does not replace the product's separate approved-asset pipeline. Sites requiring cross-origin redirects, non-HTTPS resources, POST-based rendering or unavailable browser features can fail explicitly; never quietly invent evidence.

## Private configuration

Proxy: `SCRAPER_PROXY_PASSWORD` (24–256 printable characters), `SCRAPER_PROXY_HOST` (defaults to loopback), `SCRAPER_PROXY_PORT` (defaults to 8899). The browser authenticates as username `scraper` using that password. Never publish this service as an open proxy.

Browser: `SCRAPER_BROWSER_TOKEN` (a different private credential), `SCRAPER_PROXY_URL` (private HTTP proxy endpoint), `SCRAPER_PROXY_PASSWORD`, `SCRAPER_BROWSER_HOST` (defaults to loopback), and `SCRAPER_BROWSER_PORT` (defaults to 3003). `POST /scrape` and `GET /health` require `Authorization: Bearer <SCRAPER_BROWSER_TOKEN>`. The worker should only send `{url, timeout}`; compatibility fields `wait_after_load: 0`, empty `headers`, and `skip_tls_verification: false` are accepted, not arbitrary actions. A successful response includes `content`, `pageStatusCode`, `contentType` and actual `url`.

Run the proxy with Node and `ipaddr.js` 2.3.0. The dedicated `Dockerfile` now builds non-root Node 22 proxy/browser images using a digest-pinned base and a separate npm lockfile (`ipaddr.js` 2.3.0, Playwright 1.64.0 and its matching Chromium headless shell). The main product's Playwright test dependency is separate. Chromium sandboxing is mandatory with no unsandboxed fallback. Do not use the old upstream Node 18 measurement image for production. OS packages are resolved at build time: the recipe is dependency-locked, not a bit-for-bit reproducible OS image. Record and scan the resulting image digest before promotion and rebuild for security updates.

## Build and verify the browser runtime

From the product repository root:

```sh
docker build --target proxy -t marketingbus-scraper-proxy:locked-v1 scripts/firecrawl
docker build --target browser -t marketingbus-scraper-browser:locked-v1 scripts/firecrawl
node scripts/firecrawl/verify-browser.mjs
```

To build and test the complete extraction stack:

```sh
docker build -f scripts/firecrawl/Core.Dockerfile -t marketingbus-scraper-core:locked-v1 scripts/firecrawl
node scripts/firecrawl/verify-browser.mjs --core
```

`Core.Dockerfile` verifies the SHA-256 of the exact upstream source archive, applies the checked-in patch before the full upstream TypeScript build, uses its frozen pnpm lockfile and records Rust dependencies in `core-Cargo.lock`. The Rust toolchain is fixed to 1.99.1; compilation must leave the Cargo lock unchanged. The Go compiler base is digest-pinned and Go module resolution is read-only. OS packages, the Rust installer and versioned FoundationDB client download are not all content-addressed; this is not a claim of bit-for-bit reproducibility. The runtime carries compiled code/native libraries, not the compiler toolchain or native build directory. It runs as `node`, with the existing allowlisted child environment and no application configuration copied into the image.

Upstream license, original source archive, patch, native lock and build recipe are retained under `/opt/notices`. Keep these artifacts and complete license/security review before production distribution; retaining notices alone is not that review. The Cargo lock originated from the earlier pinned-source probe and fixes both registry versions and upstream native git revisions. The prior temporary API/browser measurement images were removed after capturing their inputs as part of this replacement; the replacements are now built, and source remains available to rebuild the old probes if needed. No customer data was in those images.

The `--core` acceptance mode additionally creates a dedicated internal Redis network, a digest-pinned disposable Redis instance and the new read-only non-root core/gateway image. It checks real Markdown/final-address output, authentication denial, metadata-target rejection and child drainage/reuse. No gateway or Redis host ports are published and the browser is not a Redis-network member. All four containers and three networks are removed by the verifier.

The build context is restricted by a whitelist `.dockerignore`; no application source, customer data or `.env` files enter it. Acceptance creates uniquely named disposable containers and networks with generated test-only credentials. It checks authenticated idle readiness, non-root Node 22, sandboxed public-page extraction, final URL, private/metadata targets, certificate-expired page rejection, direct-internet denial and reuse after failures. It always attempts cleanup and reports exact names if cleanup fails. It uses public test websites, not paid APIs. Do not run against customer infrastructure or give these containers production credentials.

The browser runs read-only with bounded `/tmp` and shared-memory mounts, 512 MiB memory, one CPU, an init process, all capabilities dropped and `no-new-privileges`. Only the proxy has external connectivity. `seccomp_profile.json` is based on the [Playwright v1.64.0 Docker profile](https://github.com/microsoft/playwright/blob/v1.64.0/utils/docker/seccomp_profile.json), with one documented addition: permit Chromium's `chroot` syscall inside its user namespace even when the outer container drops all capabilities. It does not grant the parent namespace `CAP_SYS_CHROOT` or `SYS_ADMIN`. The upstream [sandbox guidance](https://playwright.dev/docs/docker#crawling-and-scraping) and Apache license are retained (`PLAYWRIGHT-LICENSE`). The local first attempt correctly failed because the upstream capability-conditional `chroot` rule was excluded; the additional syscall rule allowed sandboxed startup without capability escalation. Hosting must support this namespace/seccomp combination; do not remove the sandbox to bypass a hosting limitation.

Gateway: run `core-gateway.mjs` with `FIRECRAWL_API_KEY` (private gateway credential), `FIRECRAWL_CORE_ROOT` (absolute pinned engine directory), `PLAYWRIGHT_MICROSERVICE_URL` (the complete private `http://…/scrape` endpoint), `SCRAPER_BROWSER_TOKEN`, and a dedicated private `REDIS_URL`. `SCRAPER_GATEWAY_HOST` defaults to loopback; `SCRAPER_GATEWAY_PORT` defaults to 3002. Both `GET /health` and `POST /v2/scrape` require Bearer authentication. Health confirms the gateway is listening, not that all dependencies have been accepted. The request contract is exactly the application's single-page Markdown request; AI extraction, actions and expanded options are rejected.

The gateway forks `core-job.cjs` for one admitted job with a 256 MiB JavaScript heap, a 35-second deadline and forced termination after a one-second shutdown allowance. It waits for child exit before accepting its result. Child logs are discarded; only bounded Markdown and selected metadata cross the IPC boundary. Application, supplier, session and gateway credentials are not copied into the child environment. Run this in a dedicated source image without application `.env` files or host filesystem mounts; an environment allowlist is not a substitute for process/container isolation. Redis is dedicated to the scraper, not Marketingbus's customer database. No second queue or cross-business cache is introduced.

Apply `standalone-browser.patch` to upstream Firecrawl commit **`ef12eb36b2f3382838dfe0a0c1a5add3d5df7fe5`** before its normal TypeScript build. It adds private browser authentication, requires actual final-URL provenance and prevents URL-specific engine overrides when `MARKETINGBUS_PRIVATE_INTAKE=true` (set by the gateway). The wrapper explicitly selects `proxy: "basic"`, `skipTlsVerification: false`, one Playwright engine and the supplied bounded timeout. These are important: upstream's default automatic proxy choice expanded a 30-second request to 120 seconds, and its normalizer otherwise enabled TLS-verification skipping. Do not remove the explicit private profile or silently fall back to hosted/paid engines.

## Application acceptance follow-up (20 October 2026)

Run `node scripts/firecrawl/verify-browser.mjs --application` from the application root after building the three locked local images. This implies `--core` and adds a new temporary PostgreSQL database, applies the real application migrations, and runs the actual `manageSource`, `runOneSourceJob`, `listSources` and evidence-review service path using real HTTP and public DNS. It does **not** use provider API keys or existing customer records.

All **22 runtime/application checks passed** locally: the previous 14 runtime checks, temporary-database startup, and seven application checks for queuing/deduplication, actual Markdown/hash persistence, cached reuse without automatic approval, exact-excerpt/tenant boundaries, real certificate failure without retry, expired-lease recovery, and source deletion. The first iterations exposed test-harness connection/argument issues; those were corrected before recording this successful run. No product/API-route change was needed. This proves the service/worker/database path, **not** an authenticated browser onboarding session or production deployment.

The runner uses synthetic credentials and an empty database named `scraper_acceptance`; the application probe refuses non-loopback URLs, a different database name, production mode, paid execution, or a nonempty user/organization dataset. A disposable, loopback-published relay exposes exactly the gateway and fixture database to the local Node process. The gateway and browser retain their internal-only networks, and the browser is not a fixture-database peer. This relay is test tooling, not production architecture. Cleanup removes only the six containers and three networks created by this invocation, including the memory-backed fixture database. Existing databases are untouched. Application subprocess diagnostics redact fixture credentials; Docker command arguments are never logged.

Hosting review used Railway's [private-network documentation](https://docs.railway.com/networking/private-networking) and [outbound-network documentation](https://docs.railway.com/networking/outbound-networking). These describe encrypted environment-private communication and outbound connectivity, but do **not** establish support for this tested custom seccomp profile, user namespaces, or per-service default-deny egress. Do not interpret a private hostname as proof that direct internet or database access is blocked. Hosting feasibility remains unverified; no paid scraper service was created and no isolation attestation was enabled.

Read-only production checks found web, worker and PostgreSQL deployments successful. A seven-point, one-hour metric sample averaged 0.1202 GB web memory, 0.1890 GB worker memory and 0.0669 GB database memory. This is a short resource observation, not billed usage or a load test. Railway's [published pricing](https://docs.railway.com/pricing) includes plan minimums as well as resource charges; the $10/customer/month target must include the first customer's share of fixed costs, storage, network, peaks and scraper hosting. AI costs remain separate. Neither these samples nor local scraper idle measurements prove that target.
